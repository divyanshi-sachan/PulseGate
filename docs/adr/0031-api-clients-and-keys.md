# ADR-0031: API clients and keys

- **Status:** Accepted
- **Date:** 2026-10-23
- **Source:** Phase 2 design questions (user chose all recommended options); PRD FR-02; tech_impl §2.1.C, §10.2
- **Relates to:** ADR-0003 (static config), ADR-0011/0018 (errors), ADR-0014 (`auth.required`), ADR-0021 (`X-API-Key` stripped)

## Decision

### Where clients live
- A **separate clients file** at `PULSEGATE_CLIENTS` (default `config/clients.yaml`, gitignored). A committed
  `config/clients.example.yaml` holds a local-only demo client. It is validated at startup with the same strict
  Zod + `ConfigError` machinery as the routes config, and can be mounted read-only like a secret.
- If any route has `auth.required: true` (the default) and there is no clients file, **startup fails**. If no route
  needs auth, the file is optional.

```yaml
clients:
  - id: demo-client          # identifier rules as route ids
    name: "Demo client"      # optional
    enabled: true            # default true
    keys:                    # at least one
      - id: "2026-10"        # unique within the client
        sha256: "<64 hex chars>"
        expiresAt: "2027-01-01T00:00:00Z"   # optional, ISO 8601 with offset
```

### Keys
- Format: `pg_` + 32 random bytes in base64url (46 characters), generated by **`pnpm keygen`**. The raw key is shown once and
  the script prints a ready-to-paste YAML snippet. **Only the SHA-256 hex digest is stored.** A raw key in the file
  (`key:`, or a `sha256` value starting with `pg_`) is a startup error that points to `pnpm keygen`.
- Verification: a cheap format check, then SHA-256 of the presented key and one `Map` lookup by digest. A slow
  password hash isn't needed for 256-bit random keys. Looking up by digest doesn't reveal key material through timing.
- A digest may belong to only one client and key (duplicates fail validation).

### Rotation and revocation
- Clients have one or more keys, each with an optional `expiresAt`. **Rotate:** add a new key, migrate callers, remove the old one.
  **Revoke:** remove the key, or set `enabled: false` on the client. Changes take effect on **restart** (static config).
  Expiry is checked per request.

### Authentication behavior
- The key is read from `X-API-Key` only. A missing, malformed, unknown, expired, disabled or repeated header always gets
  **401 `AUTHENTICATION_FAILED`** with the same body, so nothing reveals which check failed.
- The internal reason (`missing | malformed | unknown | expired | disabled`) goes into the request log line as `authFailure`,
  with `clientId`/`keyId` on success. **Never the key or its hash.**
- **Authorization:** any valid, enabled client may call any route with `auth.required: true`. Per-route allowlists
  (and a 403 code) are deferred to their own ADR.

## Consequences
- `clientId` becomes the rate-limit identity on authenticated routes (ADR-0032) and appears in request logs.
- Tests: valid key; each failure reason gives the identical 401; expiry at the boundary; disabled client; rotation with two
  live keys; schema rejects raw keys, duplicate ids and duplicate digests; startup fails when auth is needed and the file is missing.
