# ADR-0047: First full benchmark run and its findings (real-data testing, step 4)

- **Status:** Accepted (findings; two follow-up decisions are open as Q15 and Q13)
- **Date:** 2026-10-24
- **Reports (committed; generated by `scripts/bench-report.ts` from raw files only):**
  - `benchmarks/reports/20261024T105735Z-apple-m5-full.md` (all scenarios): **104 gates passed,
    2 failed** (both K8-tput-2).
  - `benchmarks/reports/20261024T111906Z-apple-m5-full.md` (K8 repeat 1): 12/12 gates passed.
  - `benchmarks/reports/20261024T112243Z-apple-m5-full.md` (K8 repeat 2): 2 gates failed (K8-tput-1).
  - Raw files stay in `benchmarks/reports/raw/<run-id>/` (git-ignored); each report lists their SHA-256.
- **Environment (from the report):** Apple M5 (10 logical CPUs), Docker 29.6.1 on Docker Desktop (10 CPUs, 7,936 MiB),
  gateway limited to 2 CPUs / 512 MiB, k6 2.3.0 in a container on the Compose network. The runs were made at commit
  `9458b23` plus 3 uncommitted files (the k6 CPU sampling fix and its test, committed together with these reports).
  **Local measurements on one machine, not production capacity claims.**

## What the run showed (numbers copied from the reports)
- **Correctness held under load** everywhere except the finding below:
  - **K4:** 37,502 HITs reconciled across k6, `/metrics` and the admin API; 0 upstream requests for the key.
  - **K5:** every subject's accepted count was inside its derived interval.
  - **K8-shared:** within its interval across 2 instances.
  - **K3:** route shares within ±2 points.
  - **K2:** 4,347 allowed / 11,152 rejected = `/metrics` decisions.
- **Gateway overhead (K1 − K0, informational).** At 250 / 500 / 1,000 rps offered: Δp50 0.60 / 0.28 / 0.11 ms,
  Δp99 2.36 / 3.21 / 2.05 ms; no dropped iterations. The direct baseline's own p50 also falls as the rate rises
  (0.35 → 0.21 ms), which points to CPU-idle effects at low rates on this host. One run is not a baseline.
- **K9 saturation ramp:** **no sustained breach in the tested range** (up to 3,967 responses completed in the last full
  second). Gateway CPU peaked at 87 % of its 2 CPUs, k6 at 52 %. One isolated second breached (t+30 s: p99 195.6 ms,
  0 errors), consistent with the stalls described below. This is not a capacity figure: the limit wasn't reached.
- **K7 (20 % upstream failures, retries, breaker):** 20.19 % of attempts failed; the breaker opened 3 times. Of 15,002
  requests, 1,303 got 503: **1,200 `CIRCUIT_OPEN`** and 103 upstream 503s that passed through after the retries ran out.
  - With retries, one bad request can contribute up to 3 consecutive failed attempts towards the breaker's threshold
    of 5 (failures are counted per attempt, ADR-0024). Under random 20 % failures the breaker therefore opened about
    every 20 s, and each 2 s open period rejected about 400 requests.
  - This is the configured behaviour working as specified, not a bug. Whether that trade-off is wanted for "flaky but
    alive" upstreams is a configuration question (raise `failureThreshold`, or reduce retries); no change is made here.

## Finding: fail-closed 503s from a 50 ms Redis command timeout during VM-level stalls
- **Observed, intermittently:** `RATE_LIMITER_UNAVAILABLE` (fail-closed 503) during the Redis throughput scenarios at
  500 rps. Across 3 runs × 2 scenarios (about 37,500 requests each): **1, 0, 0, 0, 12 and 0** such responses.
  Everything was counted and reconciled correctly (k6 = `/metrics` = the limiter-unavailable counter).
- **Not an overload:** Redis CPU stayed at or below 6 %, gateway CPU below 50 %, and k6 below 26 %.
- **Correlation, measured:** `pulsegate_nodejs_eventloop_lag_max_seconds` reached **101.9 ms** and **94.1 ms** in exactly
  the two windows with failures, and stayed at or below 39 ms in the windows without. In the second case, the **idle**
  second gateway also stalled for 93.8 ms at the same time.
- **Interpretation (supported, not proven):**
  - A pause of the whole Docker Desktop VM stalls every container.
  - When the gateway's event loop resumes, timers run before I/O callbacks, so ioredis's 50 ms `commandTimeoutMs` fires
    even if Redis had already replied.
  - `redisFailurePolicy: closed` then turns the timeout into a 503 (ADR-0034).
  - Confirming this needs a run on native Linux, where Docker Desktop's VM is not in the path.
- **Decision for now:** the gate stays strict (it caught a real behaviour), and the reports are committed with their
  FAILs, not replaced by a clean rerun. The default timeout is **not** changed unilaterally; see **Q15**.

## Request deduplication (Q13): still unanswered
- No stampede was observed, but none could have been. K3's cold cached key reached the upstream once, because requests
  arrived about every 5.6 ms and the mock answers in about 1 ms. K4 is warmed by design.
- Deciding Q13 needs a dedicated scenario: a cold key, a slow upstream (e.g. 300 ms) and many concurrent requests,
  counting the upstream calls per key with the mock's `/_stats`. Q13 therefore stays deferred, with that as its
  evidence requirement.

## Report generator changes made while reading the results (same raw data, regenerated)
- **Run IDs use a neutral label** (`BENCH_HOST_LABEL`, default `local`), never the hostname, because they become
  committed file names. These 3 runs were relabelled `apple-m5` and regenerated from unchanged raw files.
- **Server errors are counts with a precise share** ("1 (0.0027 %)"); the first version rounded the real error to
  "0.00 %".
- **K9** distinguishes isolated breaching seconds (stalls) from saturation (≥ 3 consecutive seconds). The first version
  reported the stall at t+30 s as if it were the first point of saturation.
- **k6's own CPU is sampled** (re-listing the project's containers every round), so a load-generator ceiling would be
  visible. This was fixed before the run.
- K8 shows each instance's CPU and the count of `RATE_LIMITER_UNAVAILABLE`.

## Consequences
- Performance thresholds remain informational (review point 6); one full run is not a repeatable baseline.
- **Next measurements worth having:** the same suite on native Linux (Q15), a stampede scenario (Q13), and 2 more full
  runs on this machine to see the run-to-run spread.
